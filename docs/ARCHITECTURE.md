# 系统架构

设计目标只有一句话：**网站发布之后不需要任何人管理它。**

新模型发布、旧模型退役、价格调整、榜单更新，全部自动反映到页面上；
上游数据源挂掉、改字段、限流，网站都不会坏。

---

## 一、整体链路

```
     每 12 小时（GitHub Actions cron）
                  │
                  ▼
   ┌──────────────────────────────┐
   │  scripts/sync                │
   │  ① 抓取（ETag 条件请求）      │──→ data/raw/*.json     原始快照，用于回放
   │  ② 归一化（单位/日期/SPDX）   │
   │  ③ 字段级仲裁 + provenance   │
   │  ④ 合理性校验闸门            │──✗ 不通过则拒绝写入，保留旧数据，非零退出
   │  ⑤ 原子替换                  │──→ data/models.json    唯一数据契约
   └──────────────────────────────┘
                  │
                  ▼
        git commit & push（只提交 data/，精灵图不进仓库）
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
   Vercel 构建          EdgeOne 构建
   （海外访问）          （国内访问）
        │                   │
        └── prebuild: scripts/sprites 由 data/models.json + 角色设定表
            确定性画出 606 张精灵图（约 7 秒），再跑 next build
```

**精灵图不提交进仓库。** 它是可再生产物：由已提交的角色设定与字符画（`scripts/sprites/chibi/`）
与已提交的 `data/models.json` 确定性生成，整轮约 7 秒。
不提交的理由是合成器只要改一次绘制逻辑，就会一次性产生十几 MB 的新 blob，
几次迭代就能把仓库撑爆。构建时生成还有一个额外好处：产物必然与数据一致，不会脱节。

关键性质：**前端在运行时不请求任何上游 API，也不持有任何密钥。**
页面读的是仓库里的静态快照，构建时就已经确定。

## 二、为什么是静态快照而不是运行时拉取

三个理由，按重要性排序。

**上游挂掉时网站照常显示上一次的好数据，永远不白屏。** 这是运行时拉取做不到的。

**前端不碰任何 API key。** 没有密钥就没有泄漏风险，也没有需要人续费的东西。

**git 提交历史本身就是一套自动积累的「模型世界快照库」。**
每天两次提交，一年之后就有了七百多个时间点的完整世界状态，
这正好可以喂给时间线页，让它展示的不只是「模型什么时候发布」，
而是「这个世界在每一天分别长什么样」。这个资产越早上线越值钱，而且完全免费。

代价是数据新鲜度以半天计而非秒计。对一个模型信息站来说，这个代价可以忽略，
真要抢时效还可以随时手动触发一次同步。

## 三、技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 框架 | Next.js 16 静态导出（`output: 'export'`） | 纯静态产物，两个平台都能直接托管 |
| 样式 | Tailwind CSS 4 | |
| 角色渲染 | DOM / CSS sprite，服务端渲染 | canvas 与 WebGL 里的内容对爬虫和屏幕阅读器完全不可见，而这个站的流量主战场是内容页 |
| 中文像素字体 | Fusion Pixel Font（OFL-1.1） | 商用免费无署名义务；子集化后实测 9.4 KB |
| 图像合成 | sharp | |
| 脚本运行 | tsx | |

**关于不用 PixiJS**：广场是排排站的布局而非可漫游地图，DOM 足够。
PixiJS v8 完整 min bundle 实测 800 KB / gzip 225 KB，对一个以内容和 SEO 为主的站点不划算。

**关于中文像素字体的坑**：Zpix 有三千多个 star，很多人以为它是开源字体，
实际上单个商业产品授权 ¥7000，而且版权声明明文禁止「拆分」——网页子集化恰恰就是拆分，
也就是说付了钱之后子集化这一步本身仍然违约。改用 OFL-1.1 的 Fusion Pixel Font。

## 三点五、精灵图的身份 / 状态分层

这是一个容易被误改回去的决策，单独说明。

**精灵图只烘焙「这个模型是什么」**——身体、发型、五官、服饰、鞋、眼镜、耳机、
画笔调色板、钥匙、工具腰带。这些只有模型本身变了才会变。

**状态层由前端 DOM 现画**——皇冠（排名每天在变）、思考光环、新生闪光（30 天必然过期）、
雾化斗篷、幽灵态。

好处是排名一变、下次构建当场摘冠，**不需要重新合成任何一张 PNG**，
而且 DOM 层不受 64 像素画布限制，皇冠能画得比烘焙时清楚得多。
拆分后精灵图总体积从 18.4 MB 降到 11.5 MB。

代价是前端要知道「头在哪」。这靠 manifest 里合成时实测的 `anchors`
（head / skull / body 三个包围盒）解决——**不能硬编码百分比**，
头顶高度会随体型、发型体积、有没有戴耳机而变，实测两个角色的颅骨顶能差 3 像素。

`manifest.json` 顶层的 `overlaysBaked: false` 是两条管线之间的握手信号。
前端读它而不是写死，这样万一哪天合成器改回烘焙，也不至于画出双份皇冠。

## 四、零维护的边界在哪

系统里唯一依赖人类常识的地方是**厂商形象母题**（`src/data/vendor-registry.ts`）：
机器能从数据里读出 DeepSeek 的定价和上下文长度，但读不出「DeepSeek 应该是一头鲸鱼」。

处理方式是把它做成一张**查表而不是一段逻辑**：

- 表里有的厂商，用专属形象
- 表里没有的厂商，自动落到 `wanderer`（神秘旅人），斗篷颜色由厂商 id 的稳定哈希决定，大陆归属由总部国家推导
- 任何情况下都不会失败、不会白屏、不会阻塞管线

仓库是公开的，任何人都可以提 PR 给新厂商补一行。**这相当于把零维护的最后一块短板交给社区，
而不是交给一个需要续费的 API。**

同理，中文名的缺口也不会造成故障：未收录厂商在中文页面直接显示英文原名。
`Reflection AI` 对中文读者完全无障碍，而且比机器瞎翻更专业。

## 四点五、前端的三层：数据 → 标尺 → 视图

前端不是「读 JSON 直接渲染」，中间隔着一层**标尺**，这一层是理解代码的关键。

```
data/models.json                     构建期读入的静态快照
        │
        ▼
build*Scale(allModels)               ← 标尺层：必须喂全体模型，不能只喂当前页要显示的
  buildAptitudeScale  能力条填充比例
  buildPriceScale     价格档位
  buildSizeScale      体型档位
  buildValueScore     性价比
  buildPersonaContext 「谁在哪个域里是第一」
  buildTraitContext   各维度排名
        │
        ▼
scale.xxxOf(model)                   ← 视图层：逐个模型问标尺要档位
```

**为什么必须分这一层**：全站所有档位都是「在当前全体模型里的分位」而不是绝对阈值
（理由见 HANDOFF 第五节）。分位需要看到整个人群，所以标尺一定要用
`snapshot.models` 全集构建，而不是当前页面要渲染的那几十个。
搞混会得到很隐蔽的错误——比如只喂广场阵容的话，
「记性」会因为旗舰模型普遍是百万上下文而全部顶格，条子就白画了。

唯一的例外是**稀有度裁剪**（`assignTraits` / `buildVisualPruning`）：
它问的是「这一屏里这个元素是不是太常见」，所以必须只喂同屏展示的那批。
「百万记性」放在 484 个模型里算稀有，放在一屏旗舰里就人手一块了。

## 五、文案为什么不会胡说

所有页面文案由结构化字段套模板生成，**不展示上游返回的任何自由文本**，
也不调用任何 LLM 生成人设描述。

这带来两个后果，都是好的：一是模型信息永远不会被编造——
对一个使命是「让人看到真实状态」的网站，这是底线；
二是中英双语没有翻译延迟，因为同一份数据渲染两次即可，新模型进来两边同时到位。

具体到「一句话人设」这种最容易想调 LLM 的地方，做法是
**从宽到窄枚举「维度 × 限定域」，找出这个模型排第一的最宽说法**
（`src/lib/persona.ts`）。产出的是「开源模型里综合智力最强的模型」
「十强里最划算的模型」这类句子——纯查表、排序、字符串拼接，离线确定性可复现。

生硬来自泛化而不是模板：「一款性能优秀的大语言模型」对谁都成立所以对谁都没用，
而「在某个域里排第一」这个条件从结构上保证了同一句话在全站最多属于一个模型。

首版只做中文，英文的 i18n 结构同期搭好，不留技术债。

## 六、双端部署

| 平台 | 面向 | 触发方式 |

| Vercel | 海外访问 | git push 自动构建 |
